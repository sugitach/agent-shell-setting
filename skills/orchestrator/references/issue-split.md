# 規模判断・再帰的 Issue 分割・Issue 選択

planner は規模判断と sub-issue 作成、reviewer は分割計画レビュー、親（orchestrator）は承認確認・Issue 選択・状態保存を担当する。
分割は運用上の判断と記録で扱い、行数の自動計測や依存関係の自動管理を前提にしない。

## 規模判断と粒度

- planner は選択された Issue ごとに、単一 PR の差分がおおよそ1000行超になりそうかを判断する。対象ファイル数・変更種別などから概算し、根拠を短く残す。厳密な行数見積は不要。
- 超えない見込みなら従来の実装計画を作る。超えそうなら分割計画を選ぶ。
- 分割粒度の基準は「各 Issue が単独でテストを通せること」のみ。必要な依存先が統合された後、その Issue の変更とテストだけで検証できることを意味する。明記した依存先以外の、未着手の兄弟 Issue の実装まで必要とする分け方は避ける。
- 分割直後に各子を1000行以下へ収めることは強制しない。子を選択した時点でも概算し、なお大きければ同じ手順で再帰的に分割する。意味のあるテスト可能な単位より細かい、機械的な分割はしない。
- 親と同じ範囲の子を作るだけなど、分割に進展がない場合は作成・再分割を繰り返さず、制約と未解決事項を親へ返す。親は blocked として、要件を変えずに進める選択肢を整理する。

## sub-issue の作成と分割計画

planner は必要な数の sub-issue を実際に作成し、親子関係と各 Issue URL を記録する。本文は次の形を使う。

```markdown
## 親と担当範囲
Parent: <親 Issue URL>
担当する親の要件: <番号または原文への対応>
担当する親の DoD: <番号または原文への対応>

## 背景
<この子で解決する問題>

## 要件
<担当範囲の具体的な要件。親の要件を書き換えない>

## DoD
- [ ] <この子の完了条件と検証方法>

## 依存関係
Depends on #<前提 Issue 番号>
<別リポジトリの場合は Issue URL も併記。複数なら各前提を列挙、なければ「なし」>
```

分割計画には規模判断、親の全要件・DoD と子の対応表、作成した子の URL 一覧、依存関係、各子の単独テスト方法を記す。親の統合確認に残る DoD も対応表に明記し、その根拠となる子の成果物・検証を対応づける。
Issue 作成権限がなければ未作成の本文案と理由を返し、作成済みとは報告しない。一部だけ作成された場合は作成済み URL と未作成分を分けて記録し、再開時の重複作成を防ぐ。
分割を選んだ planner はその Issue の coding 計画へ進まず、分割計画を親へ返す。

## 分割計画レビュー

reviewer は親 Issue と実際に作成された子の本文を確認する。

- 子の担当範囲と対応表が、親の要件・DoD を過不足なく網羅するか。必要な統合確認が抜けていないか。
- 親にない仕様の追加や、親の要件・DoD の書き換えがないか。
- 依存関係に欠落、参照先の不明確さ、自己依存・循環依存などの矛盾がないか。
- 必要な依存先の統合後に各子が単独でテストを通せるか。分割が進展しており、過度な細分化になっていないか。1000行以下かどうかは承認条件にしない。

問題があれば根拠と修正方向を添えて changes_requested を返し、親を通して planner へ差し戻す。作成状況・本文などを確認できなければ blocked とし、推測で承認しない。
approved は対象の分割計画版と子 Issue 群の本文を特定して返す。対象が変わった場合は再レビューする。

## Issue 選択と再帰

1. 親は sub-issue がすべて作成済みで、現在の分割計画・子の本文に対するレビューが approved であることを確認する。未作成・未承認なら coding にも再選択にも進めず、修正待ちまたは blocked として理由を保存する。
2. 分割が承認された親 Issue は、直接 coding する候補から恒久的に除外する。親を open のまま保持していても再選択しない。coding へ進まず Issue選択へ戻り、その未完了の子を候補に加える。
3. 候補集合の分割済み親、完了済み、着手中の Issue を除き、各 Issue 本文の依存関係を確認する。依存なし、またはすべての前提がマージ済みで依存解消を確認できた Issue から、依頼の優先順位に沿って次を選ぶ。依存未解消・確認不能な Issue は選ばない。
4. 依存先が分割済み親なら、その子孫すべての成果物のマージ・完了と、親の DoD を満たす統合確認をもって依存解消とする。Issue の close だけ、子の一部完了、PR 作成・CI 成功だけでは解消扱いにしない。
5. 選んだ子を planner へ渡し、規模判断から再開する。再分割した子は新たな親となり、同じ作成・レビュー承認を経て候補から除外され、未完了の孫が候補になる。再帰を理由に新しい親セッションを起動しない。
6. 選択可能な Issue がなければ、候補と未解消の依存・不足する確認を記録して停止する。循環依存は planner に修正を依頼し、外部のマージ待ちなどは blocked とする。状態変化の根拠なく同じ候補の再選択・ポーリングを繰り返さない。全子孫が完了している場合は親の統合確認へ進む。
7. 子孫のマージ・完了と統合確認を満たした親から順に、完了・依存解消を記録し、許可された範囲で親 Issue の状態更新・close を行う。マージ権限は既存の工程に従い、分割を理由に自動マージしない。

分割・選択の記録と承認対象は [handoff.md](handoff.md) に従って保存する。修正回数は再分割や Issue 選択でリセットせず、同一原因についてタスク全体の上限を引き継ぐ。
